# Lot 0.3 — Cross-targets, lavapipe image, `xtask build` and `package`
- Model/effort: Sonnet, medium | Depends on: 0.2 | Milestone: none

## Goal
Build placeholder binaries for the four Docker-buildable targets, run one headless Vulkan test on lavapipe, and package the binaries with checksums.

## Crates
- Owned: `xtask` (extend `build`, `package`), a placeholder binary crate `probe` (or equivalent name, see Spec) used only to prove the toolchain, `Dockerfile` and `docker-compose.yml` (targets and lavapipe test wiring).
- Forbidden: the `xtask` public command names created in 0.2 must not change.
- Read-only: `CLAUDE.md`, `docs/plan.md`.

## Spec (condensed)
Targets built in the `dev` image:

| Target | Method |
|---|---|
| `x86_64-pc-windows-msvc` | `cargo-xwin` |
| `aarch64-pc-windows-msvc` | `cargo-xwin` |
| `x86_64-unknown-linux-gnu` | native |
| `aarch64-unknown-linux-gnu` | cross linker and sysroot |

macOS targets (`aarch64-apple-darwin`, `x86_64-apple-darwin`) are NOT built here; they are built by the CI macOS runners in 0.4. Do not add them to `xtask build`.

Plan phase 0 wording "four binaries, one headless Vulkan test": one placeholder binary per Docker target above, four binaries in total. Each prints its version and exits 0.

Lavapipe: Mesa lavapipe is the software Vulkan ICD in the `dev` image, with Vulkan validation layers enabled. It allows rendering without a screen. The test must create a Vulkan instance and device through lavapipe and read a single offscreen pixel, with no window and no surface. Validation-layer messages count as failure (acceptance rule for every render lot).

Commands:
- `build --target <t>`: builds the binary for `<t>` (one of the four targets). Output under `dist/<target>/`.
- `package`: for each built target, writes an archive (`.zip` for Windows, `.tar.gz` for Linux) plus `SHA256SUMS` listing every archive.
- Windows-to-Windows and Linux-to-Linux targets use the same command; no host installs.

Note: the Windows client is copied from `dist/` to the host to run on the real GPU in later phases. Nothing is installed on the host for it.

## Public interfaces to create or respect
- `cargo xtask build --target <t>` where `<t>` is one of the four target triples above.
- `cargo xtask package` produces `dist/*.zip|*.tar.gz` and `dist/SHA256SUMS`.
- The probe binary's output line format: `probe <version> <target>`, exit code 0.

## Acceptance criteria
- `.\dev.ps1 build --target x86_64-pc-windows-msvc` and the same for `aarch64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` each produce a binary under `dist/` (four binaries total).
- `file dist/x86_64-unknown-linux-gnu/probe` (or equivalent) reports ELF x86-64; the Windows outputs are PE32+ files.
- One test (`cargo nextest run -p <lavapipe-test-crate>` or a test in `xtask`) creates a Vulkan device on lavapipe, renders or clears one offscreen image, reads one pixel back, and passes; zero validation-layer messages in its output.
- `.\dev.ps1 package` produces the archives and `dist/SHA256SUMS`, and `sha256sum -c dist/SHA256SUMS` passes inside Docker.
- `.\dev.ps1 ci` still exits 0.

## Out of scope
- macOS builds and MoltenVK (0.4 and CI).
- The real client and dedicated server (Phase 1 and later); the probe is a placeholder only.
- Release publication (0.4).
- Accepting licences outside the image config.
