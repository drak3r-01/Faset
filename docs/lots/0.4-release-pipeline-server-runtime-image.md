# Lot 0.4 — `release.yml` tag pipeline, macOS build, `server-runtime` image
- Model/effort: Sonnet, medium | Depends on: 0.3 | Milestone: J0 (reached when this lot is done)

## Goal
Add the single GitHub Actions pipeline that runs only on version tags, producing a full release (archives, checksums, notes, container image) from a trial tag.

## Crates
- Owned: `.github/workflows/release.yml`, `Dockerfile` target `server-runtime`, `xtask` (`maps validate` and tag/version check helper if needed), version bump in root `Cargo.toml` if required by the trial tag.
- Forbidden: the probe and cross-target configuration from 0.3 (only read them).
- Read-only: `CLAUDE.md`, `docs/plan.md`.

## Spec (condensed)
Trigger: exactly one workflow file, `on: push: tags: ['v*']`. No trigger on branch push or pull request.

Stages, each depending on the previous:
1. `test`: runs in the `dev` image, executes `xtask ci`. Also checks that the tag (`vX.Y.Z`) equals `[workspace.package] version`. Mismatch fails the stage.
2. `build`: depends on `test`. Matrix of six targets:
   - Four in the `dev` image: `x86_64-pc-windows-msvc`, `aarch64-pc-windows-msvc`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`.
   - Two on macOS runners: `aarch64-apple-darwin`, `x86_64-apple-darwin`, native build with MoltenVK embedded.
3. `release`: depends on `build`. Creates the GitHub release with all archives, `SHA256SUMS`, and release notes generated from commit messages. Publishes the `server-runtime` image to the GitHub Container Registry (ghcr.io).

A failure in a stage stops the following stages, so no release is published when a test fails.

`server-runtime` image: Debian slim plus the `dedicated` binary, for running the standalone server. At this lot `dedicated` does not exist yet; use the probe binary as the placeholder entrypoint and document that it is replaced in lot 1.x. Image tags: version and `latest` (lot decision; the plan only says the image is published to ghcr.io).

Versioning: semantic versioning; tag `vX.Y.Z` triggers the release (plan section 6 defines only this format). Trial tag for this lot: a pre-release tag such as `v0.0.1-rc.1` is a lot decision, not in the plan; it deviates from `vX.Y.Z`, so report it. Use it only if the workspace version matches it (set `version` accordingly in the same PR), otherwise it fails by design.

Because GitHub CI runs only on tags, `cargo xtask ci` run locally in Docker is the only quality gate before merge.

## Public interfaces to create or respect
- Tag format `v<semver>`, must equal the workspace version.
- Release assets: `<crate-or-probe>-<target>.(zip|tar.gz)` and `SHA256SUMS`, as produced by `cargo xtask package` from 0.3.
- Image: `ghcr.io/<owner>/<repo>/server-runtime:<version>` and `:latest`.

## Acceptance criteria
- `actionlint` (run in Docker, or via the workflow lint step) reports no error for `release.yml`.
- Pushing a trial tag `v<workspace-version>` on a test branch or fork produces: `test` green, six `build` jobs green (including both macOS jobs), a `release` with six archives and `SHA256SUMS`, and an image pushed to ghcr.io.
- Verification: `sha256sum -c SHA256SUMS` on the downloaded release passes.
- A deliberately failing test on the trial tag stops the pipeline before `build` (checked once, then reverted).
- `.\dev.ps1 ci` exits 0 before merge.

## Out of scope
- Real game binaries, the real `dedicated` server (lot 1.x onward).
- Tags for real releases (lot 7.3 for `v0.1.0`).
- Any workflow other than `release.yml`; no branch CI.
- Code signing and notarisation of macOS binaries.

## Session protocol
1) Read `CLAUDE.md` and this file.

3) Branch `lot/0.4-release-pipeline`; all commands run in Docker only, never on the host (the macOS jobs run only in GitHub CI and are verified there).

5) Conventional Commits in English, e.g. `ci: add tag-triggered release pipeline`; one lot = one branch = one PR; run `graphify update .` after code changes.
6) Short report: delivered, tests passed, deviations (state if the trial tag was not run and why).
