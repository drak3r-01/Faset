# Lot 7.1 — Profiling and optimisation of rendering and network
- Model/effort: Sonnet, medium | Depends on: phase 6 complete (no explicit list in the plan) | Milestone: none

## Goal
Every budget in section 20 is measured by a test or a recorded check and met, without changing public interfaces.

## Crates
- Owned: none. Fixes may touch any crate, but only internal code.
- Read-only: all public interfaces. Any fix that changes a public interface means stop and report.

## Spec
Profiling:
- `puffin` (pure Rust), shown in the debug overlay with frame times, the network graph and simulation statistics.

Budgets to meet (section 20):
| Measure | Budget |
|---|---|
| Server tick, 16 players including bots | < 2 ms on one core |
| Dedicated server memory | < 200 MB |
| Client 1080p, mid-range GPU | 144 fps |
| Client on integrated GPU with FSR 1 | 60 fps |
| CPU time per frame | < 4 ms |
| Draw calls | < 500 |
| Map load | < 2 s |

Network budgets (measured in test, with 100 ms latency, 20 ms jitter, 5 % loss):
- mean prediction error < 5 cm;
- downlink < 100 kbit/s per client at 16 players;
- no durable state divergence between client and server.

Endurance: 16 bots for 10 simulated minutes, no panic, no memory growth.
Robustness: random and truncated packets sent to the server never panic.

## Public interfaces to create or respect
- Do not change any public signature. Add benchmarks and tests only (`benches/` or test modules).

## Acceptance criteria
- `dev.ps1 test` and `dev.ps1 render-test` pass, including a benchmark/test per budget row that asserts the budget.
- CPU-side budgets (tick, draw calls, CPU frame, map load, memory, network) measured in Docker (lavapipe for render).
- GPU budgets (144 fps, 60 fps iGPU) measured by running the client from `dist/` on the Windows host (plan allows this for real GPU); results recorded in the PR description.
- `dev.ps1 ci` passes, including `cargo deny`.

## Out of scope
- New features; balance changes; platform packaging (lot 7.2).

## Session protocol
1. Read `CLAUDE.md` and this file.
2. Do not use graphify until the repo contains Rust code; then query it (`graphify query`, `path`, `explain`) before grepping.
3. Branch `lot/7.1-profiling-optimisation`. All commands run in Docker (`dev.ps1 <cmd>`), never on the host, except the GPU check described above.
4. Run `dev.ps1 ci` (= `cargo xtask ci`) before merge; it is the only quality gate.
5. Conventional Commits in English; one lot = one branch = one PR; run `graphify update .` once code exists.
6. Short report: delivered, tests passed, each budget with its measured value, deviations from this file.

Conventions: repo content in English; metres/seconds/radians; `thiserror` in libraries, `anyhow` in executables, `tracing` for logs; never change a crate's public interface you do not own.
